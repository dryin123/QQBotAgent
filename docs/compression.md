# 上下文记忆

## 问题

QQ 群与单聊的消息不限轮数累积，会话上下文会无限增长。超出模型窗口后请求报错或费用激增，超出部分被静默截断，早期信息丢失。

单纯压缩成自然语言摘要能省 token，但每压一次糊一层：第 10 次摘要里，第 1 轮的内容基本只剩模糊印象。

6.0 起改为**结构化记忆**。

## 机制

1. 按 `user_id + group_id` 分组维护会话，组按 `max_rounds` 轮自动翻篇；
2. 每条消息到达时估算该组 token 总量（含既有记忆）；
3. 超过有效阈值时后台触发一次记忆抽取，不阻塞当条消息回复；
4. 抽取 = 把「既有记忆 JSON + 本轮对话」交给模型，输出更新后的记忆 JSON；
5. 写入 `history_temp/<uid>_g<gid>/memory.json`，同时渲染成紧凑文本写入 `summary.txt`（界面展示与旧版本兼容用）；
6. 压缩后保留最近 2 轮原文，其余原文由记忆覆盖；
7. 注入上下文时优先读 `memory.json`，没有则回退读 `summary.txt`。

## 记忆结构

```json
{
  "version": 1,
  "updated": 1690000000,
  "user": {"nick": "小明", "traits": ["养猫", "上夜班"]},
  "facts": [{"k": "工作", "v": "便利店夜班", "t": 1690000000}],
  "tasks": [{"task": "帮他写周报", "status": "open"}],
  "relations": {"小明-猫": "两只"},
  "events": ["聊到排班表"]
}
```

合并规则：

- `facts` 按 `k` 覆盖，新值替换旧值，键上限 80 条
- `tasks` 按任务名覆盖，`status` 取 `open` / `done`
- `events` 按内容去重，只保留最近 40 条
- `traits` 去重，上限 20
- 模型输出的字段类型不可信，统一纠正后再落盘

## 相比摘要的收益

同一段对话，结构化记忆渲染后的 token 量通常只有自然语言摘要的三到五成，且同 key 直接覆盖，不会随压缩次数衰减。

实测（单元测试 `TestCompressionFlow`）：864 token 原文 → 20 token 记忆，保留称呼、事实、事件三类信息。

## 失败处理

抽取可能因网络、额度、密钥、超窗失败，也可能模型不按 JSON 输出。

- 返回内容不是合法 JSON：降级为文本摘要写入 `summary.txt`，不浪费这次调用
- 请求失败或返回空：按 `user_id:group_id` 记指数退避，60s → 120s → 240s → …，封顶 1800s，成功一次清零

没有退避的话，阈值不会因失败而回落，每条新消息都会重新调一次模型。

## 阈值与模型窗口

OpenAI 兼容接口不返回上下文窗口大小，需在界面按模型手填「模型上下文窗口」（`model_context_tokens`，默认 32768）。

```
effective_limit = min(compression_token_limit, model_context_tokens * 0.6)
```

窗口填 0 表示不按窗口收敛。记忆长度上限同样按 `effective_limit // 20` 计算。

这条约束的意义：接 8k 窗口的本地模型时，60000 的阈值会让请求本身超窗，抽取永远失败并进入退避，上下文再也压不下去。

## 并发

- 防重入按用户隔离，同一用户同时只跑一个抽取任务，不同用户互不影响
- 抽取请求在会话锁外执行：单次调用耗时以秒计，持锁会让所有用户的消息处理一起阻塞
- 写回时以当前 history 的尾部为准，抽取期间新追加的消息不会丢
- 抽取期间若该组已翻篇，结果丢弃，不写入错误的组

## 调参

| 场景 | 建议 |
|---|---|
| 省钱、对话短 | `compression_token_limit` 调低到 20000~30000 |
| 长任务、需要完整上下文 | 调高到 80000+，`max_rounds` 调到 20~50 |
| 本地小模型 | `model_context_tokens` 按实际窗口填，否则阈值无效 |

默认 `max_rounds=5` 时组内最多 5 轮，通常达不到阈值，记忆抽取不会触发。要它真正工作，把 `max_rounds` 调到 20 以上。

## 归档

摘要和记忆都是有损的。为了不把原文彻底丢掉，被挤出去的对话会写入 SQLite 的 `archive` 表。

**什么时候归档**

- 记忆抽取后，被摘要覆盖掉的那部分原文
- 组翻篇时，旧组的全部原文

**归档不参与常规上下文**

它不加载进内存，不进每次请求，不占 token。只有一条消息命中关键词时，才取回几条拼进上下文。归档可以随时删除，删了不影响会话、记忆和任何正在运行的逻辑。

**检索方式**

先切词再打分，不是整句匹配。

按虚词把句子切成实词块，短块丢弃，长块再在块内生成 2 到 3 字片段。这样「你还记得我养的那只猫吗」抽出的是「记得」「只猫」，能命中「记住了」「养了两只猫」；按固定窗口滑会切出「你还记」「得我养」这类原文里根本不存在的碎片，一条也命不中。

打分规则：命中词越多分越高，长词权重更大，同分按时间近优先。

命中后带上下文：把命中记录前后各一条一起返回，避免只召回一句孤零零的回复。

`archive_fts` 仍用 FTS5 trigram 建索引，启动时做一次 `integrity-check`，坏了自动 rebuild。

这是关键词检索，不是语义检索：能命中「提到同一个词」的历史，命不中「意思相近但用词不同」的内容。

**实测对比**

| 查询 | 整句 LIKE | 切词打分 |
|---|---|---|
| 你还记得我养的那只猫吗 | 0 | 1 |
| 汤圆最近怎么样 | 0 | 2 |
| 我那两只猫叫什么 | 0 | 2 |
| 上周看什么电影了 | 0 | 1 |
| 今天天气不错 | 0 | 0 |

最后一行是对照：没有相关历史时不能误召回。「什么」这类高频词在停用表里，不会制造假命中。

**容量**

单用户 `archive_keep`（默认 5000）超出丢最旧的；全库 `archive_keep_total`（默认 200000）防止多群累加撑爆磁盘。

**注入格式**

```
[归档检索]
2026-10-24 用户：我在便利店上夜班，养了两只猫
2026-10-24 机器人：记住了，夜班注意休息
```

条数由 `archive_recall_top` 控制（默认 4），单用户总量由 `archive_keep` 控制（默认 5000，超出丢最旧）。

**删除即消失**

数据库开了 `secure_delete=ON`，删除会覆写数据页，不是只把索引标记为可复用。有测试验证：写入标记文本、删除、再扫文件字节，扫不到。

`--archive-purge` 和 `--clear-sessions` 之后会自动 `VACUUM` 回收空间。

自动备份已取消。原来每小时把全量会话 dump 成明文 JSON 保留 10 份，等于把「删除」变成「十小时内还能找回来」。需要备份请手动 `--export-sessions`，导出的是明文，用完自己删。

**本地查看与删除**

```bash
python main.py --archive-stats
python main.py --archive-list <user_id> [条数]
python main.py --archive-search <user_id> <关键词>
python main.py --archive-purge <user_id>
```

# 上下文压缩算法说明

## 背景与动机

QQ 群/单聊消息不限轮数累积，会话上下文（history）会无限增长，超出大模型上下文窗口后：

- 请求体过大导致 API 报错或费用激增；
- 超出部分被静默截断，丢失早期关键信息。

本项目在 `SessionManager` 中实现了**滚动合并压缩（v2，原创实现）**：

1. 按 `user_id + group_id` 分组维护会话（组按 `max_rounds` 轮自动翻篇）；
2. 每收到一条消息先估算该组历史 token 总量（含既有摘要）；
3. 超限（`compression_token_limit`，默认 60000）且存在可压原文时，在后台触发一次压缩（不阻塞当条消息回复）；
4. 压缩执行 = **合并**：把「既有摘要 + 本轮新增对话」一次性交给大模型，输出一份合并摘要，覆盖写入 `history_temp/<uid>_g<gid>/summary.txt`（单份滚动，不无限累积文件）；
5. 压缩后**保留最近 2 轮原文**（`history` 尾部），其余原文被摘要化——近况细节不丢；
6. 后续 `get_context` 注入「滚动合并摘要 + 保留的近轮原文」。

## Token 估算

`_estimate_tokens` 采用中英混合启发式（无外部 tokenizer 依赖）：

- ASCII 字符：约 4 字符 / token；
- 中文/全角字符：约 0.75 token / 字；
- 每条消息固定 +10 系统开销。

精度足够用于压缩阈值判定；如需精确计费请以 API 返回的 usage 为准。

## 触发策略

- 检查在收到每条消息时执行（`maybe_compress`），**压缩任务在后台执行**（`asyncio.create_task`）；
- `_compressing` 防重入标志：同一时刻只有一个压缩任务在跑；
- 防空转：无可压原文（history 为空）时不触发；
- 压缩完成后保留近 2 轮原文，token 大幅回落，天然避免短时间内重复触发。

## 压缩质量保障

- 压缩 prompt 明确要求保留：用户偏好、进行中的任务、重要决定、待办事项、人名与数字；
- 第二次及以后的压缩**会把既有摘要一并并入**（提示"勿遗漏既有摘要要点"），长期记忆逐层衰减大幅缓解；
- 摘要目标长度约 `max(500, compression_token_limit // 20)` token；
- 旧版（v1）产生的 `compress_NNN.txt` 文件仍可被读取并在首次压缩时合并进 `summary.txt`，随后自动清理，升级无痛。

## 阈值调优指南

| 场景 | 建议 |
|---|---|
| 追求省钱、对话短平快 | 开激进：`compression_token_limit` 调低（如 20000~30000） |
| 长任务需要完整上下文 | 调高（如 80000+）或关闭自动压缩；同时调大 `max_rounds`（如 20~50）让压缩真正接管长对话 |
| 中文为主 | 默认启发式已按中文字加权，无需调整 |

> 注：默认 `max_rounds=5` 时组内最多 5 轮对话，通常达不到压缩阈值——压缩主要服务于"调大 max_rounds 的长对话"场景；如需机器人长期记忆，建议把 max_rounds 调大到 20+ 并开启压缩。
